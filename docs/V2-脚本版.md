# V2：Kunlun 简化结构脚本化部署与 Web 构建平台

V2 只能自动化已经在全新虚拟机验证通过的 V1 手工步骤。当前 Web 平台已经实现仓库分析、站点凭据、离线制品库、bootstrap/app-update 构建 Worker 和 `install-app-update.sh`；真实 Docker 打包、独立 `r2` 初始化包和数据库迁移更新仍需在可用 Docker Engine 与另一台全新虚拟机上完成交付验收，因此当前不能宣布脚本版生产验收完成。

## 1. 自动化边界

V2 只提供两条主流程：

```text
build-bootstrap + install-bootstrap    # 全新服务器首次安装
build-app-update + install-app-update  # 后续应用和数据库升级
```

不再实现：

- `packages/releases/current` 管理；
- 全栈 release 软链接切换；
- 每个应用版本重复打包四个中间件；
- 运行时 `kunlun.env` 生成和迁移；
- 自动回滚中间件数据。

## 2. 构建完整初始化包

目标命令：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-bootstrap.ps1 `
  -AppVersion 1.1.1 `
  -PackageRevision r2 `
  -Platform linux/amd64
```

输出：

```text
dist/kunlun-bootstrap-1.1.1-r2-linux-amd64.tar.gz
dist/kunlun-bootstrap-1.1.1-r2-linux-amd64.tar.gz.sha256
```

构建脚本必须：

1. 检查 Docker、Buildx 和 Compose。
2. 构建 backend/frontend 固定标签镜像。
3. 检查四个固定中间件镜像存在。
4. 检查六个镜像均为 `linux/amd64`。
5. 六个镜像分别生成 tar 和同名 SHA256。
6. 生成简化目录包，不创建 `packages/releases/current/state/config.env.example`。
7. 检查两份 Compose 不含 `${...}`，不依赖 `.env`。
8. 不打印明文地检查两份 Compose 账号和密码一致。
9. 使用两份 Compose 分别执行 `config --quiet`。
10. 生成 manifest、images.txt 和包内 SHA256SUMS。
11. 生成外层 tar 和 SHA256。
12. 重新解压到临时目录完成一次自检。

## 3. 构建应用更新包

目标命令：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-app-update.ps1 `
  -FromVersion 1.1.1 `
  -ToVersion 1.1.2 `
  -Platform linux/amd64
```

输出：

```text
dist/kunlun-app-update-1.1.2-linux-amd64.tar.gz
dist/kunlun-app-update-1.1.2-linux-amd64.tar.gz.sha256
```

应用更新构建脚本必须拒绝以下内容：

- Docker 安装文件；
- 中间件镜像 tar；
- middleware Compose；
- data 或 backup 文件；
- 与目标版本无关的旧应用 tar。

manifest 必须明确：

```text
PACKAGE_TYPE=app-update
FROM_VERSION=1.1.1
TO_VERSION=1.1.2
TARGET_PLATFORM=linux/amd64
DB_MIGRATION_REQUIRED=true|false
DB_MIGRATION_TOOL=manual|flyway|liquibase|none
```

## 4. 首次安装脚本

目标命令：

```bash
bash scripts/install-bootstrap.sh --root /opt/Kunlun
```

脚本阶段：

```text
[1] 校验 root、架构、系统命令、端口和磁盘
[2] 校验包内 SHA256 和 manifest
[3] 建立简化目录和权限
[4] 检查或安装 Docker/Compose
[5] 首次 load 前确认 Docker data-root
[6] 安装两份 Compose、镜像 tar、SQL 和运维脚本
[7] 导入六个镜像并校验平台/ID
[8] 初始化四个数据目录 UID/GID
[9] 创建 kunlun-net
[10] middleware config + up --wait
[11] 中间件健康门禁
[12] app config + up --wait
[13] /api/health/all 验收
[14] 备份和恢复演练提示
```

脚本必须可安全重跑，但遇到已有未知数据时必须停止并请求人工判断，不能自行删除或覆盖。

## 5. 应用更新脚本

目标命令：

```bash
bash scripts/install-app-update.sh \
  --root /opt/Kunlun \
  --package /opt/Kunlun/tmp/kunlun-app-update-1.1.2-linux-amd64.tar.gz
```

脚本阶段：

```text
[1] 校验当前 middleware/app 健康
[2] 校验更新包类型、起始版本、目标版本和 SHA256
[3] 检查更新包没有中间件内容
[4] 不显示值地校验新旧 Compose 凭据一致
[5] 备份当前 app Compose 和 MySQL
[6] 安装并导入新 backend/frontend 镜像
[7] 如有需要，停止 app 并执行数据库 precheck/up/verify
[8] 原子替换 application/compose.app.yml
[9] 只执行 app up --wait
[10] /api/health/all 和业务验收
[11] 写升级日志
```

虽然不再使用 `current/state`，替换单个 Compose 文件仍应使用同目录临时文件和原子 `mv`：

```text
compose.app.yml.new → config --quiet → mv 覆盖 compose.app.yml
```

## 6. 密码规则

- 密码直接存在两份 Compose，因此构建包是站点专用流程。
- 构建和安装日志不得输出 Compose 展开内容。
- bootstrap 时两份 Compose 必须一致。
- app-update 时新 app Compose 必须与在线 middleware Compose 一致。
- 应用升级不承担密码轮换；检测到变化必须停止。
- 密码轮换需要单独 SOP，同时修改中间件内部账号和 app Compose，不能靠重启完成。

## 7. 数据库迁移规则

- 每个应用更新 manifest 必须明确是否需要迁移。
- 有迁移时必须提供 precheck、up、verify 和回退说明。
- 迁移前必须生成可校验的 MySQL 备份。
- 脚本不能根据目录是否为空猜测是否需要迁移。
- Flyway/Liquibase 尚未接入前，手工 SQL 必须记录执行版本和结果。
- 破坏性迁移不能自动回滚；需要恢复数据时转人工停机流程。

## 8. 日志和失败规则

日志写入：

```text
/opt/Kunlun/logs/deploy/
/opt/Kunlun/logs/upgrade/
/opt/Kunlun/logs/backup/
/opt/Kunlun/logs/restore/
```

任何阶段失败必须：

- 返回非零退出码；
- 保留容器和日志现场；
- 不删除中间件 data；
- 不执行 Docker prune；
- 不打印密码；
- 不把中间件失败伪装成应用部署成功；
- 数据库迁移后不擅自切回旧应用。

## 9. V2 验收顺序

1. 先在全新虚拟机完整复验 V1 `1.1.1`。
2. 实现并复验 bootstrap 构建脚本。
3. 实现并复验 bootstrap 安装脚本。
4. 制作一个无数据库变化的 `1.1.2` 更新包并升级。
5. 制作一个有向前兼容数据库迁移的更新包并升级。
6. 分别演练应用回退和数据库恢复。
7. 全部通过后才把 V2 标记为可交付。
